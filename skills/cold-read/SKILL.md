# cold-read

세션에서 일한 Claude가 쓴 문서는 **세션을 본 사람에게만 읽힌다.** 문장이 틀린 게 아니라, 독자가 갖지 못한 맥락을 전제로 쓴다. 쓴 쪽은 그 맥락을 지울 수 없어서 다시 읽어도 못 찾는다.

그래서 검사는 맥락이 없는 쪽이 한다.

## 독자

문서가 실제로 누구에게 가는지로 고른다. 기본은 동료다.

**동료 (기본)**: 같은 팀이고 이 세션은 안 봤다.

- 아는 것: 프로젝트 이름, 팀 스택, 팀에서 원래 쓰는 용어, 분야 상식
- 모르는 것: 이 세션에서 무엇을 시도했고 무엇이 막혔는지, 세션 중에 붙인 이름, 버린 안, 대화로만 오간 수치의 출처

**고객사 담당자**: 문서가 회사 밖으로 나갈 때(안내문, 작업 요청, 회신). 제품을 쓰는 사람이고 우리 내부 구성요소 이름은 모른다.

- 아는 것: 자기 쪽 환경, 제품 화면과 쓰는 방법, 자기가 다루는 인프라 도구
- 모르는 것: 내부 구성요소 이름, 우리 팀 용어, 사내 검증 환경, 우리가 왜 이렇게 하는지
- 고객 독자는 정보 외에 **"이걸로 무엇을 답하거나 결정할 수 있나"**를 본다. 문서에 고객에게 묻는 항목이 있으면 독자 프롬프트 4번을 그 항목별로 묻는다

어느 독자든 그 독자가 아는 걸 풀어 쓰지 않는다. 아는 걸 설명하면 그것도 소음이다.

## plain-ko와 나눈 범위

| | plain-ko | cold-read |
|---|---|---|
| 보는 것 | 문장의 수사 | 글과 독자 사이의 간격 |
| 판정 근거 | 글만 보면 된다 | 독자가 무엇을 모르는지 알아야 한다 |
| 비유 | 멋부렸나 | 모르는 사람이 풀 수 있나 |

순서는 cold-read 먼저, plain-ko 나중이다. 빈틈을 메우며 새로 쓴 문장도 다듬어야 하기 때문이다.

## 절차

### 1단계 — 쓸 때 규칙

취합 문서를 쓸 때 처음부터 지킨다. 검사에서 걸릴 것을 줄이는 단계다.

- **세션에서 만든 이름은 처음 나올 때 정의한다.** `B안`, `R2 패킷`, `그 우회로`처럼 대화 중에 생긴 이름이 정의 없이 나오면 안 된다. 한 번만 쓰이면 이름을 버리고 내용을 쓴다.
- **비유를 메커니즘으로 바꾼다.** `밑 빠진 독이었다` → `재시도할 때마다 큐에 같은 작업이 다시 쌓였다`. 비유를 남기려면 바로 뒤에 무엇을 가리키는지 적는다.
- **지시어는 문서 안을 가리켜야 한다.** `앞서 본 문제`, `그 방식`이 가리키는 대상이 이 문서 앞쪽에 있는지 확인한다. 세션 안에만 있으면 대상을 다시 적는다.
- **결론만 쓰지 않는다.** A에서 C로 갔으면 B를 거친 이유를 한 문장이라도 쓴다. 특히 버린 안은 왜 버렸는지가 동료에게 가장 쓸모 있다.
- **화살표 체인을 푼다.** `가설→기각→재설계`는 쓴 사람에게는 요약이고 읽는 사람에게는 목차다. 단계마다 무슨 일이 있었는지 문장으로 쓴다. 코드 흐름, 데이터 흐름처럼 화살표가 원래 맞는 자리는 둔다.
- **수치에는 무엇을 어떻게 쟀는지 붙인다.** `302→278`이 아니라 `p95 응답시간 302ms→278ms, 부하 테스트 100rps 10분`.

### 2단계 — 맥락 없는 독자에게 읽히기

**새 서브에이전트**를 띄운다. `subagent_type`은 `general-purpose`. `fork`는 대화 맥락을 물려받으니 쓰지 않는다.

프롬프트는 `references/reader-prompt.md`의 틀을 그대로 쓴다. 채우는 칸은 둘이다.

- 문서 파일 경로
- 독자가 아는 것 한두 줄 (프로젝트 이름, 스택, 팀 공용 용어)

틀은 동료용과 고객사용 두 개다. 고른 독자에 맞는 쪽을 쓴다.

**프롬프트에 세션 내용을 넣지 않는다.** "이 문서는 ~를 정리한 것이다" 같은 배경 설명도 넣지 않는다. 맥락을 흘리는 순간 검사가 무효다. 독자가 아는 것 칸에도 세션에서 처음 나온 정보는 쓰지 않는다.

**독자가 아는 것 칸에는 확실한 것만 쓴다.** 도구 목록을 짐작으로 채우면 거기 없는 도구가 전부 "처음 본다"로 올라온다. 예를 들어 "Prometheus/Grafana 를 안다"고만 적으면, 팀이 원래 쓰는 Kibana가 미정의 용어로 걸린다. 모르겠으면 넓게 쓴다("팀 공용 도구를 안다").

문서가 아직 파일이 아니면 스크래치패드에 저장하고 그 경로를 준다.

**고객사 독자면 독자를 두 번 띄운다.** 같은 프롬프트로 새 서브에이전트 둘을 동시에 띄운다. 큰 빈틈은 매번 나오지만 세부 항목은 실행마다 갈린다. 두 보고에 모두 나온 항목을 먼저 고칠 것으로 올리고, 한 번만 나온 항목은 따로 묶는다. 밖으로 나가면 되돌리기 어려운 문서라 서브에이전트 한 번 비용을 더 쓴다. 동료 독자는 한 번만 띄운다.

### 3단계 — 대조

서브에이전트가 돌려준 것 중 가장 쓸모 있는 건 **절마다 바꿔 쓴 한 줄**이다. "이해 안 됨"보다 잘못 이해한 채 넘어가는 경우가 훨씬 많고, 그건 바꿔 쓴 문장을 의도와 비교해야만 드러난다.

각 절에 대해 묻는다. 바꿔 쓴 한 줄이 내가 전하려던 것과 같은가?

- 같다 → 통과
- 다르다 → **오독**. 원문 어디가 그렇게 읽히게 만들었는지 찾는다
- 바꿔 쓰지 못했다 → **막힘**

미정의 용어와 추측 목록은 그대로 후보가 된다. 다만 독자가 원래 아는 용어(팀 공용어, 분야 상식)가 올라왔으면 지운다. 서브에이전트는 팀 사정을 모르니 이런 오탐이 섞인다. 독자가 아는 것 칸을 좁게 써서 생긴 오탐이면 보고에 그렇게 적는다.

**쓴 사람이 이 세션이 아닐 때.** 사용자가 기존 문서를 넘겨 검사를 맡긴 경우, 메인 Claude도 의도를 모른다. 그때는 이렇게 한다.

- 독자가 추측한 것 중 원본(코드, 스크립트, 설정, 함께 있는 다른 문서)으로 맞는지 확인할 수 있는 것은 확인한다. 보고에 근거 위치(`파일:줄`)를 붙인다
- 원본으로 확인할 수 없는 것은 "문서만 보고 판단"으로 따로 묶는다
- 의도를 알아야만 고칠 수 있는 항목은 사용자에게 묻는다. 짐작으로 교정 후보를 만들지 않는다

### 4단계 — 보고

```
오독 (n건)
  §절 제목  독자가 읽은 것: …
            의도한 것: …
            원인: 원문 "…" (어떤 증상인지)
            교정 후보: …

막힘 (n건)
  §절 제목  어디서 막혔는지
            교정 후보: …

미정의 용어 (n건)
  "용어"  처음 나온 줄  → 정의 문장 후보 / 이름을 버리고 풀어 쓸 문장

추측 (n건)
  줄  독자가 추측한 것 → 맞았나 틀렸나, 교정 후보

통과: §…, §…
```

고객사 독자로 두 번 띄웠으면 각 항목 앞에 `[2/2]` 또는 `[1/2]`를 붙이고, `[2/2]` 항목을 위에 둔다.

고쳐 쓴 전문을 내지 않는다. 사용자가 항목을 고르면 그것만 반영한다. 반영한 뒤 plain-ko로 넘긴다.

통과한 절도 적는다. 안 적으면 검사하지 않은 절과 구분이 안 된다.

## 하지 말 것

- 메인 Claude가 스스로 다시 읽고 검사를 끝내기. 맥락이 있는 쪽은 못 찾는다
- `fork`로 독자를 띄우기
- 독자 프롬프트에 배경 설명 넣기
- 독자가 아는 것 칸을 짐작으로 채우기
- 동료가 아는 것까지 풀어 써서 문서를 늘리기
- 문체 지적을 섞기. 그건 plain-ko 몫이다
- 서브에이전트 보고를 걸러내지 않고 그대로 전달하기
